双版本数据库存储物理隔离规范 (v1.38)

系统为传统本地版 (mengya-local) 与容器微服务版 (mengya-docker) 建立了底层数据的 100% 物理硬隔离机制：

  • 传统本地版：默认严格固化使用宿主机独立单文件 SQLite (mengya-local/db.sqlite3)，切断上级目录环境变量污染，开箱即用；
  • Docker 容器版：使用专属 PostgreSQL 18 容器，数据持久化于命名卷 pgdata，端口 5432 仅在 Compose 内网暴露，不对宿主机映射；
  • 两者在数据存储介质、物理路径与网络访问上完全解耦，彻底杜绝数据交叉与冲突。

孕育阶段全域自适应协同规范：胎教故事周数智能跳转与交互对齐 (v1.42)

  • 医学特性平滑适配：胎儿听觉始于孕17周，孕早期用户（1~16周）进入时智能吸附至第17周，并展示科普温情提示框；

.env 环境变量持久化与数据库存储模式动态重配规范 (v1.43)

为保障系统配置安全性并提供极致运维体验，系统建立了规范化的数据库模式重配与引导体系：

  • 操作禁忌说明：不建议直接删除或清空 .env 文件，以防 SECRET_KEY（造成登录 Session 失效）与自定义端口重置；
  • 三种重选方式：
    1. 命令行重配（推荐）：执行 ./run.sh reconfig 或 ./run.sh start --reconfig 交互重选，或通过 -m <mode> 单行切模；
    2. 配置精准修改：编辑 .env 修改 DB_MODE=...，或仅删除该行以重新唤起向导；
    3. 全量重置：删除 .env 时系统自动从 .env.example 初始化。
  • 帮助模块与说明函数：底层通过 bin/db.sh 的 show_db_reconfig_guide() 驱动，在 ./run.sh help 中完整呈现。

PostgreSQL 镜像动态探针感知与零硬编码复用规范 (v1.44)

为满足异构服务器环境下的弹性兼容与零重复下载，系统全面重构镜像探针与共享容器决策链路：

  • 用户自定义镜像绝对遵从：支持通过 --db-image <IMAGE> 指定具体版本，本地不存在时精准拉取指定版本，严禁被本地旧镜像强制覆盖；
  • 本地已有镜像优先自动复用：未指定时优先复用宿主机运行中容器镜像及本地已有 PG/Alpine 镜像（pull_policy: never），杜绝网络带宽浪费；
  • 内置默认轻量镜像兜底：本地彻底无现存镜像时，自动下载内置成熟轻量镜像 postgres:15-alpine；
  • 共享模式去除硬编码：彻底剔除 pgvector-18 写死值，支持动态容器感知、停止容器拉起自愈与无可用容器智能平滑降级。

Docker 版本与传统版本全维度数据隔离规范 (v1.49)

彻底解决传统版本部署后再次部署 Docker 版本可能发生的数据库容器退出故障（container mengya-pg exited (1)），确立双版本物理与逻辑数据全链路隔离与 6 种部署组合防冲突矩阵：

  • 命名空间与容器名隔离：Docker 版 APP_NAME 默认为 mengya_docker，数据库专属容器名为 mengya_docker-pg，后端容器名为 mengya_docker_backend，与传统版 mengya_local 全面隔离；
  • 数据库凭据与实例名隔离：默认数据库用户 mengya_docker、密码 mengya_docker123、库名 mengya_docker，无论是独立容器还是共享容器模式均具备完全专有的库和账号；
  • 挂载路径标准化修复：数据挂载目录标准化为 /var/lib/postgresql/data，修复原先挂载至 /var/lib/postgresql 导致容器退出启动失败的缺陷；
  • 容器生命周期重启策略：所有容器（backend、redis、worker、db）统一使用 restart: unless-stopped，禁止使用 always。

10.13 根除静默降级SQLite缺陷、项目级动态data存储与DB就绪等待机制 (v1.51)

10.13.1 故障现象与根本原因深度剖析

在 Docker 版本启动与数据库切换过程中，曾出现报错 django.db.utils.OperationalError: unable to open database file。核心原因包括：

  • 静默回退隐患：原 settings.py 包含 1.5 秒 Socket 探测与静默降级逻辑，当 PG 容器在初始化或 DNS 尚未解析完成时，静默退化为 SQLite；
  • 共享 PG 主机名解析未对齐：shared 模式下 POSTGRES_HOST 曾继承 db 导致解析失败；
  • Docker 挂载单文件目录误建陷阱：在 docker-compose.sqlite.yml 中挂载文件导致 Docker 将其误建为目录；
  • 路径硬编码缺陷：不应依赖服务器固定 /app 路径，必须动态获取工程路径。

10.13.2 根治改造与架构规范

  • 协议头强类型驱动：移除静默降级，凡 postgresql:// 或 postgres:// 协议头一律严格使用 PostgreSQL 引擎，报错直接暴露；
  • 前置就绪等待探针：新增 wait_for_db.py，在 migrate 执行前等待数据库端口就绪（最大 30 秒），消除冷启动时序抖动；
  • 项目级动态 data 存储：在 settings.py 中动态获取 BASE_DIR 并自动创建 BASE_DIR / "data"，SQLite 统一存放在 data/db.sqlite3；
  • 目录级安全挂载与自愈：docker-compose.sqlite.yml 改用目录挂载 ./data:/app/data（backend 与 worker 均挂载），且 bin/db.sh 自动检测清理误建目录。

10.14 独立专属 PG 默认镜像锁定 (PG15) 与宿主机越界探测解耦自愈规范 (v1.52)

10.14.1 架构缺陷与根因剖析

治理了 detect_best_pg_image() 越界偷取宿主机其他运行容器镜像、扫描规则优先匹配 pgvector、默认 PG15 优先权被架空以及 .env 误写死 DB_IMAGE=pgvector/pgvector:pg18 导致的永久锁死缺陷。

10.14.2 治理改造与技术规范

  • 探针越界解耦：彻底移除从宿主机运行容器中偷取镜像逻辑，保障专属容器镜像纯洁性；
  • 优先级阶梯重构：本地 postgres:15-alpine > 兼容官方 PG15 > 官方轻量 alpine > 兜底自动下载 postgres:15-alpine；
  • 配置纠偏机制：默认模式不污染 .env，自动纠偏清空历史残留的 pg18/pgvector 配置；
  • 容器与数据卷自愈：启动前校验已有容器镜像，不匹配则自动重建；跨大版本自动重置旧存储卷以防初始化崩溃；
  • 存储路径统一：PostgreSQL 数据目录统一规范为 /var/lib/postgresql/data。
